# 노션 이력서 정보 구조 및 작성 규약

> 본 문서의 **MUST / MUST NOT / SHOULD / SHOULD NOT / MAY** 키워드는 [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174)를 따른다. 작성 규약은 [`lib/Garden.Harness/src/convention/core/convention-authoring.md`](../../../lib/Garden.Harness/src/convention/core/convention-authoring.md)를 참조한다.

## 목적

- 외부 채용 담당자(HR 리크루터, 테크 리드)가 10초 이내에 지원자의 직무 적합성과 엔지니어링 역량을 판정할 수 있는 정보 구조(IA)를 강제한다.
- 사내 프로젝트 코드명 나열로 인한 인지 장벽을 차단하고 기술 도메인(Domain-First) 중심의 계층화를 보장한다.
- 로컬 마크다운(Local SoT)과 Notion 배포 뷰어 간의 제목·계층·표기 일관성을 확립한다.

## 적용 범위

- **기본 적용**: `resume/**/*.md` 및 `docs/portfolio/**/*.md` 내 모든 이력서, 포트폴리오, 프로젝트 기술서 및 전략 문서.
- **연동 대상**: Notion 배포 뷰어([📄 이력서 — 김예건](https://app.notion.com/p/3dd475218675811299b0e3d6b2baa43d)) 상위 폴더 및 하위 상세 페이지.
- **예외**: 서드파티 벤치마킹 분석 원문 자료 사본(`docs/portfolio/strategy/notion-resume-references.md`).

## 규칙

<a id="domain-first-hierarchy"></a>
### 1. 최상위 폴더 도메인 중심 계층화 및 단일 책임 분할 (Domain-First & Single Responsibility)

최상위 폴더는 채용 시장에서 통용되는 기술 도메인 명칭으로 구성하되, 두 가지 이상의 이질적 직무 영역을 하나의 폴더에 결합하지 않고 단일 책임(SRP) 단위로 분리해야 한다.

- ✅ **MUST** 최상위 폴더는 백엔드, 아키텍처, DevOps, 클라우드 인프라, 개발자 경험(DevEx), 웹 디자인 시스템, Windows 데스크톱, 시스템 프로그래밍, 모바일 각각을 독립된 단일 도메인 폴더로 분리한다.
- ✅ **MUST** BLE(Bluetooth LE) 및 USB 하드웨어 디바이스 연동은 모바일 도메인이 아닌 '시스템 프로그래밍' 도메인에 포함하고, 모바일 도메인은 모바일 애플리케이션 단독으로 구성한다.
- ⛔ **MUST NOT** 하나의 최상위 폴더에 두 개 이상의 직무 영역(예: `백엔드 & 아키텍처`, `DevOps & 인프라`, `DevEx & 웹 디자인 시스템`, `데스크톱 & 시스템 프로그래밍`, `모바일 & BLE`)을 묶어서 표기한다.
- ⛔ **MUST NOT** 최상위 폴더 자체를 사내 프로젝트명(예: `Monolith`, `Argon`, `Peony`, `Lithium`)으로 구성한다.
- ⛔ **MUST NOT** 최상위 폴더를 공급 주체(예: '회사 프로젝트', '개인 프로젝트', '자체 플랫폼') 기준으로 양분한다.

근거: 외부 채용 담당자에게 사내 프로젝트명은 사전 지식이 없는 생소한 암호에 불과하며, 3초 스캔 단계에서 직무 일치 여부를 파악하지 못해 서류 이탈을 유발한다.

<a id="role-first-naming"></a>
### 2. 도메인 허브 및 하위 페이지 1줄 명사형 제목 규약과 본문 내 프로젝트·키워드 명시 (Clean 1-Line Title & In-Body Metadata)

상위 도메인(`01.`~`10.`)과 하위 상세 페이지(`01.01.`~`10.03.`) 제목은 괄호·대괄호·키워드 나열·사내 프로젝트명을 배제한 간결한 1줄 명사형으로 작성하고, 관련 프로젝트명과 세부 기술 키워드는 문서 본문 상단 메타데이터 테이블에서 제공한다.

- ✅ **MUST** 상위 도메인 허브 제목은 `{2자리 번호}. {직무 도메인명}` 형식(예: `01. 소프트웨어 아키텍처`, `02. .NET 백엔드 엔지니어링`)으로 작성하며, 제목 뒤에 `(Clean Architecture, DDD...)` 같은 기술 키워드 괄호를 덧붙이지 않는다.
- ✅ **MUST** 모든 하위 상세 페이지 제목은 `{도메인 2자리}.{하위 2자리}. {핵심 설계/구축 주제 명사구}` 형식(예: `01.01. 계층 분리와 모듈화 설계`, `02.01. 클라우드 프린팅 모노레포 백엔드 및 API 게이트웨이`)으로 작성하여 노션 본문 H1이 1줄을 유지하고 사이드바·Breadcrumb에서 말줄임(`...`)이 발생하지 않도록 한다.
- ⛔ **MUST NOT** 페이지 제목에 `[대괄호 분류]`, `(사내 프로젝트/패키지명)`, 또는 3개 이상의 기술 키워드 나열(`·`, `&`, `,`)을 넣는다.
- ✅ **MUST** 제목에서 분리한 **관련 프로젝트/패키지명**(`Monolith`, `Peony`, `Argon`, `nemonic`, `Lithium`, `Garden.*` 등)과 **핵심 기술 키워드**는 삭제하지 않고, 반드시 각 문서 본문 최상단 요약 콜아웃 및 메타데이터 테이블의 `관련 프로젝트(적용 시스템)` 행과 `핵심 키워드(주요 기술 스택)` 행에 빠짐없이 명시한다.
- ⛔ **MUST NOT** 하위 페이지 번호를 상위 도메인 접두사 없이 로컬 번호(`01.`, `02.`)로만 표기한다.

근거: 제목에 분류 태그·기술 스택·사내 프로젝트명을 모두 넣으면 본문 H1이 3~4줄로 개행되어 시각적 피로도를 유발하고 사이드바/경로 표시줄이 모두 잘리므로, 제목은 1줄 주제어로 정리하고 프로젝트·기술 키워드는 본문 상단 표에서 구조적으로 제시해야 한다.

<a id="multi-disciplinary-project-dispersion"></a>
### 3. 복합 엔지니어링 생태계의 도메인별 원자적 분산

백엔드·인프라·디자인시스템·모바일이 복합된 대형 프로젝트(Peony, Garden 등)는 단일 카테고리에 가두지 않고 기능별로 분리해야 한다.

- ✅ **MUST** 복합 프로젝트는 백엔드 마이크로서비스, 클러스터 인프라, 디자인 시스템, AI 하네스, 모바일 앱 단위로 원자화하여 각 도메인 폴더에 독립 페이지로 분산 배치한다.
- ⛔ **MUST NOT** 복합 프로젝트 전체를 특정 단일 도메인(예: 백엔드) 아래 단일 페이지로 축소하거나 은폐한다.

근거: 다면적 풀스택 플랫폼 프로젝트를 단일 문서로 취급하면, 백엔드 이외의 인프라·디자인 시스템·모바일 엔지니어링 실적이 완전히 묻히게 된다.

<a id="design-system-and-devex"></a>
### 4. 디자인 시스템 및 DevEx 거버넌스의 독립 도메인 수립

전사 생산성을 견인하는 디자인 시스템과 AI 에이전트 하네스는 독립된 전문 도메인으로 격상해야 한다.

- ✅ **MUST** `Garden.Razor` & `Penpot` 웹 디자인 시스템 구축 실적을 독립된 도메인 또는 핵심 프로젝트 페이지로 명시한다.
- ✅ **MUST** `Garden.Harness` AI 코딩 에이전트 거버넌스 및 CI/CD 가속 실적을 개발자 경험(DevEx) 도메인에 명시한다.

근거: 디자인 도구(Penpot)와 C# Blazor를 잇는 토큰 파이프라인 및 AI 에이전트 하네스 구축 실적은 일반 개발자와 차별화되는 테크 리드급 역량의 핵심 증거다.

<a id="excluded-technologies"></a>
### 5. 전략적 비선호 기술 배제 및 주력 스택 집중

지원자의 전문성을 희석시키는 비선호 기술은 전략적으로 제외하고 핵심 스택에 집중해야 한다.

- ⛔ **MUST NOT** 전략적 비선호 기술인 `Flutter`를 이력서 최상위 도메인, 폴더명, 대표 프로젝트 제목에 포함한다.
- ✅ **MUST** 모바일 영역은 `Lithium` 중심의 BLE 실시간 통신 최적화 및 C#/Kotlin 네이티브 하드웨어 제어에 집중하여 기술한다.

근거: 선호하지 않는 기술 스택을 이력서 전면에 배치하면 원치 않는 직무 제안을 유발하고 핵심 강점(.NET/C#, K8s, 하드웨어 제어)의 선명도를 저하시킨다.

<a id="factual-integrity"></a>
### 6. 실증적 근거 기반 및 담백한 서술 (Factual & Understated Tone)

이력서의 모든 제목과 본문 서술은 실제 코드, 커밋 이력, 설계 문서로 즉시 입증 가능한 사실에만 기반하며 담백한 건조체로 작성해야 한다.

- ✅ **MUST** 정량적 수치(기기 제어 대수, 트래픽, 스토리지 용량, 성능 개선율, 커밋 수 등)는 저장소 기록, 아키텍처 문서, 측정 로그 등 검증 가능한 근거가 존재할 때만 기재한다.
- ⛔ **MUST NOT** 확인된 근거 없이 규모·성과·수치를 부풀리거나 호들갑스러운 표현(예: 근거 없는 `글로벌 50만 대 제어`, `100TB급 Rook-Ceph`, `전사 빌드 70% 단축`, `실패율 0%` 등)을 제목이나 본문에 사용한다.
- ⛔ **MUST NOT** 자기 평가형·홍보성 수식어(예: `혁신`, `극대화`, `고난도`, `원천 차단`, `완벽 해소`, `지속적인 가치 창출`, `역량 입증`)를 사용하거나 내부 참고용 문구(예: `(김용찬 벤치마킹)`)를 이력서 본문에 노출한다.
- ✅ **MUST** 가치 판단 형용사를 배제하고 실제로 수행한 설계, 구현, 문제 원인과 해결 방식만 담백하게 기술한다.

근거: 이력서에 과장되거나 홍보성 미사여구가 포함되면 기술 면접 및 레퍼런스 체크 과정에서 지원자 전체 이력의 엔지니어링 신뢰성을 급격히 하락시킨다.

<a id="no-internal-repo-dump"></a>
### 7. 내부 Git 저장소 전수 목록 및 감사 대시보드 노출 금지 (No Internal Repository Dump)

이력서 본문에는 채용 담당자가 이해할 수 없는 사내 Git 저장소 목록이나 내부 감사용 추적표를 노출하지 않는다.

- ⛔ **MUST NOT** 이력서 메인 페이지나 도메인 허브에 `GitHub 기여 저장소 총괄 대시보드`, `41개 저장소`, `포괄 저장소` 등 내부 Git 저장소 이름을 나열한 전수 조사(Audit) 표를 배치한다.
- ⛔ **MUST NOT** 외부인이 의미를 알 수 없는 사내 레거시/단발성 저장소 코드명(`kc5`, `kc6`, `Radium`, `Sulfur`, `MIP-301-Centerm-FW-Test` 등)을 이력서 전면에 나열한다.
- ✅ **MUST** 개별 저장소 단위의 내부 기여 추적 데이터는 로컬 아카이브(`docs/portfolio/reports/`)에서만 관리하고, 이력서에는 정제된 도메인 역량과 핵심 프로젝트 성과만 기술한다.

근거: 내부 형상 관리 단위인 수십 개의 사내 Git 저장소 이름을 이력서에 나열하면, 상단 도메인 요약표와 중복될 뿐 아니라 채용 담당자에게 해독 불가능한 암호 노이즈를 유발하여 핵심 역량의 가독성을 심각하게 훼손한다.

<a id="page-content-completeness"></a>
### 8. 도메인 허브 및 하위 페이지의 본문 완결성 규약 (5-Block Content Completeness & Vector SVG Diagrams)

모든 도메인 허브(`01`~`10`)와 하위 상세 페이지는 단순 링크 목록이나 3줄 요약에 그치지 않고, 해당 페이지 단독으로도 설계 의도와 문제 해결 깊이를 이해할 수 있는 5-Block 구성을 갖추어야 하며, 노션에서 코드 원문이 길게 노출되는 `mermaid` 코드 블록이나 텍스트가 세로로 쪼개지는 좁은 다단 컬럼(`<columns>`) 대신 **전체 폭(`960px` viewBox) 벡터 SVG 아키텍처 다이어그램 이미지**로 아키텍처 흐름을 시각화한다.

- ✅ **MUST** 각 도메인 허브 페이지는 ① 도메인 요약 테이블(`역할·스택·적용 시스템·검증 지표`, 2열 테이블은 `<colgroup><col width="140"><col width="560"></colgroup>`으로 본문 전체 폭 700px 확보), ② 벡터 SVG 아키텍처 다이어그램 이미지(`![...](notion-file-block://...)`), ③ 핵심 컴포넌트/패턴 책임 매트릭스(`table`), ④ 주요 엔지니어링 과제 및 해결 사례(`문제 배경 → 설계/해결 → 검증 결과`), ⑤ 하위 상세 페이지 목록(`<page>`)의 5개 블록을 모두 포함한다.
- ✅ **MUST** 각 하위 상세 페이지는 ① 메타데이터 요약 테이블(2열 테이블은 `<colgroup><col width="140"><col width="560"></colgroup>` 지정 필수), ② 개요 및 도입 배경, ③ 벡터 SVG 아키텍처 다이어그램 이미지 및 계층별 상세 설계 테이블, ④ 핵심 구현 및 트러블슈팅 사례(Problem-Action-Result), ⑤ 관련 페이지 참조 링크를 포함한다.
- ⛔ **MUST NOT** 노션 페이지 본문에 `mermaid` 코드 블록(Notion API 기본값인 `Split(코드+미리보기)` 모드로 인해 원시 코드가 노출됨)이나 3~4단 `<columns>` 내부의 불릿 리스트(좁은 폭으로 인해 한글/영문이 3~4글자씩 세로 줄바꿈됨)를 배치한다.
- ⛔ **MUST NOT** 도메인 허브나 하위 페이지를 아키텍처 다이어그램, 컴포넌트 설계 표, 구체적 문제 해결 사례 없이 짧은 표 1개와 불릿 몇 줄만으로 비워 둔다.

근거: 채용 담당자가 도메인 폴더를 클릭했을 때 생소한 Mermaid 원시 코드가 화면을 뒤덮거나 좁은 다단 컬럼에서 글자가 세로로 쪼개지면 가독성과 신뢰도가 급격히 떨어지므로, 고정 비율 벡터 SVG 이미지와 전체 폭 테이블(`fit-page-width="true"`)로 깔끔한 시각적 구조와 문제 해결 서사를 제공해야 한다.

## 금지 사항

- ❌ 최상위 폴더에 `[Monolith]`, `[Argon]`, `[Peony]` 등 사내 프로젝트 코드명을 1차 분류로 배치하는 행위.
- ❌ 하나의 최상위 폴더에 두 개 이상의 직무 영역(예: `백엔드 & 아키텍처`, `DevOps & 인프라`, `DevEx & 웹 디자인 시스템`, `데스크톱 & 시스템 프로그래밍`, `모바일 & BLE`)을 묶어서 표기하는 행위.
- ❌ 최상위 폴더를 `회사 프로젝트` vs `개인 프로젝트` 등 공급 주체 기준으로 분리하는 행위.
- ❌ 하위 페이지 제목을 `Monolith`처럼 프로젝트명 단독으로만 작성하는 행위.
- ❌ `Peony`의 인프라·디자인시스템·앱 실적을 백엔드 단일 페이지에 구겨 넣어 타 도메인 실적을 은폐하는 행위.
- ❌ `Flutter` 관련 명칭을 최상위 도메인 및 대표 프로젝트에 노출하는 행위.
- ❌ 객관적 근거 없이 기기 대수, 스토리지 용량, 트래픽 등 수치를 부풀리거나 호들갑스러운 과장 표현(예: `[데스크톱 클라이언트] 글로벌 50만 대 제어 & .NET 9 현대화 (nemonic)`, `100TB급 Rook-Ceph` 등)을 사용하는 행위.
- ❌ 자기 평가형 미사여구(`혁신`, `고난도`, `원천 차단`, `가치 창출`, `역량 입증`)나 내부 참고용 메모(`(김용찬 벤치마킹)` 등)를 이력서 본문에 노출하는 행위.
- ❌ 이력서 본문에 `GitHub 기여 저장소 총괄 대시보드 (41개 저장소)` 등 내부 Git 저장소 목록을 나열하는 행위.

## 점검 체크리스트

- [ ] 노션 좌측 사이드바 최상위 폴더가 단일 책임(SRP) 원칙에 따라 9개 독립 기술 도메인(백엔드, 아키텍처, DevOps, 인프라, DevEx, 웹 디자인 시스템, Windows 데스크톱, 시스템 프로그래밍, 모바일)으로 분리되었는가?
- [ ] BLE 디바이스 연동이 모바일 도메인이 아닌 시스템 프로그래밍 도메인에 포함되었고, 모바일 도메인은 모바일 단독으로 구성되었는가?
- [ ] 사내 프로젝트명(Monolith, Argon 등)이 최상위 폴더명에서 완전히 배제되었는가?
- [ ] 하위 페이지 제목이 `[직무 역할] — 성과 (프로젝트명)` 형식을 지키고 있는가?
- [ ] `Peony`와 `Garden` 생태계가 각 도메인 레이어별 독립 프로젝트 단위로 분산 표출되었는가?
- [ ] `Garden.Razor & Penpot` 웹 디자인 시스템이 독립적인 프로젝트/도메인으로 식별 가능한가?
- [ ] 모바일 영역에서 `Flutter`가 배제되고 `Lithium`의 BLE 하드웨어 연동이 선명히 부각되었는가?
- [ ] 제목과 본문의 모든 정량 지표 및 수식어에 검증 가능한 근거가 있으며, 부풀리거나 과장된 표현이 완전히 배제되었는가?
- [ ] 홍보성 미사여구(`혁신`, `고난도`, `원천 차단` 등)와 벤치마킹 실명 메모가 제거되고 담백한 건조체로 작성되었는가?
- [ ] 이력서 본문에서 내부 감사용 `41개 저장소` 대시보드 및 사내 저장소 이름 나열이 완전히 제거되었는가?
