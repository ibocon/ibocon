# 블로그 작성 컨벤션

## 적용 방법

새 글은 [블로그 작성 기준선](blog-authoring-baseline.md)과 [글 템플릿](../templates/blog-post.md)을 함께 사용한다. `authoringVersion: 1`을 선언하면 `site/scripts/Test-BlogAuthoringConvention.ps1`이 이 문서의 기계 검증 가능한 최소 규칙을 검사한다.

## Front matter

v1 글은 기존 필수 필드와 함께 다음 필드를 선언한다.

```yaml
authoringVersion: 1
audience: "topic-new-developer"
articleType: "concept"
```

- `audience`는 현재 기본 독자 토큰 `topic-new-developer`만 사용한다.
- `articleType`은 `concept`, `tutorial`, `incident`, `design` 중 하나다.
- `description`은 본문 발췌가 아니라 검색 결과와 RSS에서 독자가 얻을 문제·결과를 설명한다. 80자 이상 180자 이하로 쓴다.
- 제목은 [블로그 제목 컨벤션](blog-title.md)의 결과와 기술 맥락 형식을 따른다.

## 제목과 요약

- 첫 `## 핵심 요약`에는 문제, 독자 효용, 범위를 2~4문장으로 쓴다.
- 배경 설명이나 역사보다 결론과 위험 또는 효과를 먼저 제시한다.
- 제목과 `description`은 태그를 나열하지 않고 독자가 얻는 판단 또는 결과를 표현한다.

## 용어와 문단

- 전문 용어의 첫 등장은 쉬운 역할 설명 뒤에 원어를 병기한다. 예: "메일을 대신 전달하는 중계 서버 SMTP relay".
- 이후에는 같은 용어를 한 표기로 일관되게 사용한다.
- 한 문단은 하나의 판단만 다룬다. 원인, 영향, 해결책을 나열해야 하면 문단이나 목록을 분리한다.
- 확실한 사실, 사례에서 얻은 해석, 일반 권고를 같은 문장으로 섞지 않는다.

## Heading과 목록

- H2는 단순 주제명이 아니라 독자의 질문에 답하는 제목으로 쓴다.
- H3는 H2의 설명을 분해할 때만 사용하고, H2를 건너뛰지 않는다.
- 체크리스트는 독자가 예 또는 아니오로 판단할 수 있는 문장으로 쓴다.
- 글 유형별 필수 section은 의미가 보존되는 동의어를 쓸 수 있지만, 역할을 삭제하지 않는다.

## 코드와 그림

- 코드 블록 앞에는 코드가 답하는 질문이나 전제를 쓴다.
- 코드 블록 뒤에는 독자가 확인해야 할 입력, 출력, 또는 실패 신호를 설명한다.
- 다이어그램 하나는 질문 하나만 설명한다.
- 노드에는 역할을 우선 표기하고, 필요한 원어는 한국어 역할 설명과 함께 쓴다.
- 모든 Markdown 이미지는 빈 alt text를 사용하지 않는다. 이미지가 장식용이라도 본문과의 관계를 짧게 설명한다.

## 사고와 운영 사례

- 영향, 즉시 차단, 정상 동작 보존 확인, 재발 방지를 분리한다.
- 공개 글에는 검증되지 않은 운영 명령이나 민감한 값, 내부 식별자를 싣지 않는다.
- 관찰 범위 밖의 최초 발생 시각이나 공격 원인은 단정하지 않고 관측 한계를 함께 적는다.

## 발행 전 사람 리뷰

- 제목과 핵심 요약만 읽어도 문제와 독자 효용을 알 수 있는가?
- 첫 등장 전문 용어를 모르는 독자가 다음 문단을 이해할 수 있는가?
- 그림과 본문이 같은 결론을 설명하는가?
- 사실, 해석, 권고가 구분되는가?
- 마지막 section에 독자가 적용할 수 있는 판단 또는 행동이 남아 있는가?

자동 guard는 이 질문의 답을 판정하지 않는다. guard 통과는 최소 구조가 갖춰졌다는 뜻이며, 사람 리뷰를 대체하지 않는다.
